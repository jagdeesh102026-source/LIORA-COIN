## 2. AllocationManager.sol Business Logic Verification

### 2.1 Actual Code Implementation
In `contracts/AllocationManager.sol`:
```solidity
function executeAllocation(address buyer, uint256 amount) external nonReentrant {
    if (buyer == address(0)) {
        revert InvalidZeroAddress();
    }
    if (amount == 0) {
        revert InvalidZeroAmount();
    }

    (uint256 share70, uint256 share30) = calculateSplit(amount);

    // Pull tokens from the buyer
    token.safeTransferFrom(buyer, address(this), amount);

    // Transfer 70% allocation
    if (share70 > 0) {
        token.safeTransfer(recipient70, share70);
    }

    // Transfer 30% allocation
    if (share30 > 0) {
        token.safeTransfer(recipient30, share30);
    }

    emit AllocationExecuted(buyer, recipient70, recipient30, share70, share30, amount);
}
```

### 2.2 Forensic Analysis of Current Flow
- **Buyer**: Must already hold `amount` of OXENIQ tokens and call `token.approve(allocationManager, amount)`. When `executeAllocation` runs, **the buyer loses `amount` tokens and receives ZERO tokens in return**.
- **Recipient 70%**: Receives $\lfloor \text{amount} \times 70 / 100 \rfloor$ OXENIQ tokens directly from the buyer's balance.
- **Recipient 30%**: Receives the exact remaining $\text{amount} - \text{share70}$ OXENIQ tokens.
- **Payment Assets (BNB / USDT / Fiat)**: **NONE**. The contract has no payable fallback, receives zero BNB, and does not accept or distribute USDT.
- **Conclusion**: `AllocationManager.sol` is currently a **standalone token-splitting utility**, NOT an automated crowdsale or token purchase exchange.

## 3. The 70:30 Allocation: Three Architectural Interpretations

Because the prompt explicitly directs not to invent token economics, the project has isolated this split behind a modular contract. Here are the three formal interpretations requiring managerial selection:

### Interpretation A: Purchased Tokens Split (Buyer Penalty / Vesting Model)
- **Concept**: A buyer purchases $Q$ tokens. The contract sends $70\%$ of $Q$ to the buyer and $30\%$ to the project treasury or liquidity pool.
- **Contract Impact**:
  - Requires a new `TokenSale` contract holding an OXENIQ inventory.
  - When payment is received, `recipient70` is dynamically set to the `buyer`, and `recipient30` is set to the `treasury`.
- **Security & Economic Impact**:
  - The buyer receives only 70% of the tokens they paid for. Unless explicitly marketed as a 30% protocol development contribution or bonded vesting, retail buyers will perceive this as an aggressive 30% tax.

### Interpretation B: Proceeds Split Model (Standard Web3 Presale / Crowdsale)
- **Concept**: The buyer pays in quote currency (USDT or BNB). The buyer receives **100% of the purchased OXENIQ tokens**. The incoming payment proceeds are split 70:30 between two project destinations (e.g. 70% to Initial Liquidity Pool reserve, 30% to Operational Treasury).
- **Contract Impact**:
  - `AllocationManager.sol` must be rewritten to handle the **payment asset** (e.g., USDT / BNB) rather than OXENIQ tokens.
  - Requires a crowdsale contract that accepts USDT, routes 70% USDT to LP wallet, 30% USDT to treasury, and dispenses 100% OXENIQ to buyer.
- **Security & Economic Impact**:
  - Highly standard in Web3. Zero friction for the buyer.
  - Requires pricing oracle (Chainlink) or fixed sale price in the crowdsale contract.

### Interpretation C: DEX Liquidity Fee Sharing Model
- **Concept**: The 70:30 ratio applies to swap fee revenue or LP yields generated by the $1,000 PancakeSwap liquidity pool.
- **Contract Impact**:
  - Requires an LP vault contract that holds the PancakeSwap LP tokens, claims swap fees, and routes 70% to auto-compounding and 30% to the treasury.
- **Security & Economic Impact**:
  - High complexity; requires AMM router interfaces and fee-harvesting keepers.

## 7. Cross-Chain Protocol Feasibility: BNB Chain vs. TRON

| Criteria | BNB Smart Chain (BSC) | TRON (TRC-20) |
|---|---|---|
| **Virtual Machine** | EVM (Ethereum Virtual Machine) | TVM (TRON Virtual Machine) |
| **Token Standard** | BEP-20 (Solidity 0.8.20) | TRC-20 (TVM Compatible) |
| **Gas / Resources** | BNB (Gas wei) | TRX (Energy & Bandwidth) |
| **Default Decimals** | 18 Decimals | Usually 6 Decimals (e.g. USDT) or 18 Decimals |
| **LayerZero OFT** | Natively supported via LayerZero v2 endpoints | Requires specialized TRON TVM endpoint adapter & relayer |
| **Chainlink CCIP** | Natively supported across EVM networks | **Not natively supported on TRON** out of the box |
| **Dedicated Bridge** | Custody contract locking BEP-20 | Mint/Burn contract on TRC-20 via off-chain validator |

### Architectural Directive
- **Cross-Chain Transfer**: 1:1 asset bridge via lock/mint or OFT adapter.
- **Cross-Chain Swap**: Multi-hop execution requiring deep secondary liquidity pools on BOTH PancakeSwap (BSC) AND SunSwap (TRON).
- **Recommendation**: Do NOT deploy bridge contracts until the specific TVM adapter and verifier network are contracted and audited.
